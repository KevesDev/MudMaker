# S08 — Standalone Player Client + Third-Party MUD Compatibility

**Status:** PLANNED (no Client implementation). **Sole checklist/evidence:** [S08 tracker](../../SPRINT-TRACKING.md#s08). **Dependencies:** working S02 launchable shell and shared UI and real S07.9 loopback host; full S07 protections before public networking. Creator Editor and Host Operations are different workspaces with different intent routers, state stores and permissions. No project-build or script compiler dependency is allowed inside ClientApp.

## Scope and proof
A user can open Play without creating a game, connect to a MudMaker-hosted world or an unrelated MUD over Telnet/TLS, read/send text, save a world profile, configure appearance and shortcuts, build a personal map, and use local aliases/triggers with no code. Server-generated data cannot create UI actions, load client scripts, change theme or access the editor.

## Implementation ownership and quality bar
One `ClientApp` with `ProfileStore`, `ConnectionSupervisor`, adapter interface, `TranscriptStore`, `ClientIntentRouter`, `LocalAutomationEngine` and `PersonalMapStore`. `SharedUI` offers only components/theme/focus. Use native adapter for MudMaker typed game operations; external MUD adapter sends **text** subject to that game's grammar and cannot claim native game semantics. Mapper evidence has source/confidence; autowalk only confirmed sequential steps. All remote text/protocol bytes are untrusted.

Each assigned phase has one Builder and one **different scoped Auditor**; the Lead chooses fitting verification and any valuable user interaction. Multiple phases should fit one typical Claude session. Required decisions/fixtures are owner research; missing tech/OS/API or measured policy is BLOCKED, not a Builder research assignment. Evidence only in [tracker](../../SPRINT-TRACKING.md). No code or UI is claimed built.
