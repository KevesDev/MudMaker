## Required visual result

- All dropdowns use one thin square popup outline and closely spaced, left-aligned text rows. No individual filled rounded button tiles, large row gaps, repeated submenu title or redundant container outlines. Hover/focus/selected rows may use existing semantic feedback colors. Apply to Settings/Appearance/Theme, Go To, Build, View, Host Operations and all other consumers of the shared menu primitive.
- Buttons throughout Splash/Create/Play/Host, canvas strips, forms/dialogs, drawer headers and Output use compact square-edged chrome and consistent typography. No pill/capsule geometry, large padding or generic card-like button blocks. Preserve thin borders only where they communicate a control/group. Switches/choice controls also fit the angular compact language while retaining truthful checked semantics.
- Desktop visible controls target a 24px minimum row rather than inflated touch geometry. Use compact named control/menu padding tokens (starting at 2px vertical / 4px horizontal), narrow inter-control gaps (2–4px), panel chrome gaps about 4–6px, and zero corner radius for control/popup/panel chrome. Existing token constraints and measured text/zoom requirements govern final values; document derivations in theme-presets.md. Touch-specific hit sizing remains available for genuine touch mode and must not inflate mouse desktop controls or create overlapping invisible hit areas. Body content text and splash artwork composition do not need redesign.
- All styling values come from the token source, with any new semantic token schema/catalog metadata kept in sync. No ad-hoc CSS color/size literals or second stylesheet layer per workspace. Preserve deliberate authored custom values; do not reset preferences to conceal bad defaults. Built-in themes must both show the corrected geometry.
- Output's Problems/Test Output/Execution Trace/Build Logs choices use the same compact bordered selected-control treatment as other view/tool choices. Remove their underline/tab-line styling. Preserve one View > Output route, selected content and remembered close/reopen state.

## Interaction and menu hierarchy

- Hover, pointer/keyboard pressed and keyboard focus feedback are consistent across the same control kinds. Tool/tab/view/Host choices keep a truthful selected highlight with their existing owning UI state; choosing one updates the group selection. Momentary commands show press feedback without falsely becoming selected or implying backend success. If a tool choice lacks a visible UI selection owner, map the existing router/state before adding the minimal UI-only selection state; never fake a world operation.
- Exact hierarchy: Settings > Appearance > Theme > theme options. Theme options include bundled theme names and relevant Customize/Import/Export/Reset commands; they remain app-wide. Workspace-specific appearance controls (for example Play Timestamps) sit beside Theme inside Appearance and keep their actual existing ownership. Do not accidentally make local appearance controls global or mix them into Theme. Only currently registered controls render; unwired commands stay silent.
- Each menu level remains within the viewport, including Settings at the right edge; keyboard arrows, Escape, focus restoration and pointer/touch selection work across the additional level. No theme option duplicated at Settings or Appearance root.
