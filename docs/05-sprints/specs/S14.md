# S14 — Account & Character Studio

**Status:** PLANNED; no implementation. **Sole status and evidence authority:** [tracker](../../SPRINT-TRACKING.md#s14).

## Scope
One cohesive creator-oriented account policy, role/capability and character-creation workflow sprint. **One typed visual graph editor**, using the existing S13 graph engine, with ordinary node inspectors and reusable templates; **not** a separate form builder. Supports automatic character creation, roster selection, menus, rolls, point allocation, OOC review, persistent in-world creation triggered by actual ECS events, and custom authorized C# hooks.

## Exact prerequisites
S01 identity ADR, S03 authorization, S04 AccountId/credentials/character roster and durable cursor, S05–S06 location/permissions, S07 authentication/session binding, S08.6 real gameplay, S09 reusable Creator controls, S13 typed graph and compiled hook/effect authority. Early identity and login are prerequisites of this sprint, **not deferred into this sprint**.

## Work and handoff
S14.1–8 are the one-phase-per-Builder/Auditor small task list in the tracker. Lead dispatches one phase with exact scope, focused tests, and independent Auditor. No research or silent ADR choices by builder/auditor. A human owner can test multiple phases per Claude usage window. No fake clients or implementation evidence. Owner-facing workflows may be custom without bypassing immutable account IDs or permissions.

## Validation
Automatic entry, multiple characters, guest policy, per-character last location, duplicate login, staff review with saved drafts, point-budget/reroll enforcement, world-event item pickup (sword vs staff), idempotent rewards, scoped builder/moderator, audit trails, blocked unauthorized puppet, revoke session, versioned flow migration, C# failure/retry and text-only generic clients. All flow nodes execute through one authenticated world authority. Audit after each bounded phase; a sprint-wide review only when Lead authorizes.

## Universal tags — mandatory integration

Account/character creation profiles, starting species/class/trait and character templates have organizational tags; generated characters' gameplay tags cannot confer identity/roles or bypass permissions. This is an acceptance criterion of every phase that builds the named asset or system, not a deferred separate task. [Universal tags](../../03-contracts/universal-tags-and-organization.md) owns typed refs, storage, UI and tests.
