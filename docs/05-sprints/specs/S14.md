## Phase deliverables and exact handoff
Each phase below is a **small stand-alone vertical slice**. One Builder, then one independently scoped Auditor, with a real hands-on demonstration or runnable harness **before** checkoff. Usually more than one phase should be finishable within a single Claude usage window; if unexpectedly broad, Lead splits the phase in the central tracker *before* assigning it.

**S14.1 Platform** — Deliver: Target OS client/host checks. User test: Play on each supported target. Auditor negative case: Real environment.

**S14.2 Accessibility** — Deliver: Keyboard/touch/contrast/readers. User test: Complete no-code command. Auditor negative case: No inaccessible control.

**S14.3 Parser fuzz** — Deliver: Malformed and Unicode payloads. User test: Run automated fuzz fixture. Auditor negative case: No crash/second command.

**S14.4 Flood fairness** — Deliver: Connection+RP overload. User test: Normal user plays during flood. Auditor negative case: Memory/p95/p99 measured.

**S14.5 Privacy** — Deliver: Log and phase/observer audit. User test: Inspect private Joe/secret filters. Auditor negative case: No leak.

**S14.6 Worker sandbox** — Deliver: Crash/isolation negative cases. User test: See safe error from hostile script. Auditor negative case: No native corruption.

**S14.7 Performance** — Deliver: World+command+RP fanout benchmark. User test: Reproduce report. Auditor negative case: Actual hardware/timing.

**S14.8 Release** — Deliver: Clean install, host, save, restore. User test: Publish and play example. Auditor negative case: Independent final pass.

## Adversarial acceptance specifics
- Repeat target platform test paths; report exact versions, hardware, p95/p99, peak memory, successful/failed attack cases. Neither a diagram nor a fake client suffices.
- User should create a no-code command, connect a friend, submit one-word RP and a long privileged command, restart and recover, then try malformed client requests.

## Build/test rule
Builder selects the **smallest actual source/test modules** touched by this phase, supplies exact commands, logs and a runnable user check. No fabricated test names or simulator standing in for native functionality. Auditor reviews precisely this scope and one failure path; PASS only when evidence is real and blockers/defects are gone. Lead records commit, test, user check and Auditor PASS in [tracker](../../SPRINT-TRACKING.md), then updates the 0/N count. Do **not** run a full-suite test on each phase; full sprint closeout remains Auditor-controlled.

## Handoff contract
`phaseId; existing module/test paths; approved contract; deliverable and non-goals; targeted tests; user demo; negative oracle; evidence links; known blockers`. Research and unresolved decisions must be completed and written into the linked documentation **before** handoff. No 'research how X works' or 'choose a suitable library' Builder task.
