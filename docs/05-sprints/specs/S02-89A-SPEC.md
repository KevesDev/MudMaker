## S02.8 Catalog coverage check
One automated test (no new UI): render the Create, Play, Host and splash shells through the real app and assert every control carrying `data-control-id` exists in its workspace catalog with a test id, a registered action with exactly one owner, a keyboard path and an accessible name; and that every catalog control marked visible-on-surface for the implemented surfaces is either rendered or covered by a named deferred condition. Fix any real gap it finds in the catalog or code.
## S02.9a Theme persistence
- **Store:** one versioned preferences file in the app data folder, namespaced per the ownership list, written and read by the Rust shell (commands `read_preferences` and `write_preferences`): atomic write (temp file then rename), size limit from named configuration, schema version field, UTF-8 JSON, no secrets. Corrupt or unreadable file: keep the bytes as `preferences.corrupt-<n>` once (bounded count), start from defaults, log a structured diagnostic with the launch id; never crash.
- **What persists now:** per scope (editor, client, host, home) the selected preset id, the user theme and explicit overrides and text scale / contrast choices the ThemeManager already accepts. Values are validated by the ThemeManager on load exactly as on input; an invalid saved value is rejected token by token with a diagnostic and the last valid or the default is used.
- **Restore:** the saved selection is applied before the first paint of the first screen (no flash of the default theme); the Appearance menu still applies changes immediately and now saves them (debounced, one write in flight, last value wins, a failed write shows nothing blocking and logs a diagnostic). The Appearance UI no longer needs a "not saved" note (none is shown today).
- **Ownership:** a `PreferencesStore` in `app/src/prefs/` is the single owner of reading and writing preferences; the ThemeManager asks it, no other module touches the file.
