# 03 — User Text, Long Roleplay Posts, Descriptions and Encoding

**DECIDED field-sensitive text model.** Incoming roleplay, emotes, descriptions, bios and profiles are **content**. A newline, slash, @-prefix, quoted text, markup, CRLF or code-looking phrase has no command meaning once the message kind is `SubmitText`. The game's host may customize content bounds **within hard machine protections** but not redefine text as arbitrary code.

## Three distinct input routes
1. `CommandText(rawLine)`: one logical command selected by **message kind**; can be short, long or multiline if **that CommandDefinition's declared grammar** allows multiline argument content, while always subject to hard byte/line bounds. No auto-splitting `"say hello\n@delete world"` into two commands.
2. `SubmitText(kind, body, targetRef?)`: may be **one word or several pages**; the type is explicit, never guessed by length. Kind is a known enumeration (`roleplay.post`, `character.description`, `profile.biography`, `message.long`); body preserved as literal multiline data. The **client** presents a sizeable textbox with drafts, preview, progress counters and optional Markdown-style formatting. Server accepts exactly one typed field write; never runs embedded lines.
3. **Text-only / legacy transport** adapter: `/post` or `/desc` enters an explicit **composition state**, subsequent lines accumulate as text up to budget, and an explicit `/submit` (or independent protocol signal) saves them. Escape a literal `/submit` line with the adapter's documented quoting rule; cancel has explicit confirmation. Composition state persists only as bounded draft/session data and **never sends each line to cmdhandler**. Built-in MudMaker GUI does not need this line-oriented workaround.

## Byte, grapheme and line policy
- Validate encoded byte length **before** decoding; strict UTF-8 decoder rejects ill-formed sequences, overlong encodings and unpaired surrogates in any JSON escape. Then count Unicode scalar/grapheme clusters (Unicode UAX #29), non-empty logical lines, and maximum single-line length; no implicit byte/character equality.
- For user-authored prose **and long authored command arguments**, preserve legitimate punctuation, emoji, non-Latin scripts and meaningful combining sequences. Store canonical Unicode text as authored **without destructive blanket compatibility normalization**; field-dependent comparison keys may be normalized separately (e.g., command identifiers and character uniqueness). Rendering applies output-context encoding, not mutation of stored text.
- Normalize line terminators to LF in the **field policy** only, with explicit migration/roundtrip behavior. Zero-width and bidi controls must not be globally banned from multilingual free text; reject transport-dangerous `NUL`, malformed encoding and policy-denied control characters, and visualize/harden bidi/control text in admin logs/terminal paths.
- Before writing, field-specific validator rejects extra fields, unknown content type, unsupported markup constructs, overlimit byte/line/grapheme count, invisible/unauthorized target refs, stale version and invalid ownership. No silent cropping, partial save or conversion of rejected text to an empty string.
- Configure max fanout per audience, low-cost visibility filter and persistence record size. A 12-KiB RP post to 200 observers has large fanout cost; gateway must charge and bound it independently of input size.

## Formatting / display security
Default: **plain text** with safe renderer (DOM text node, React escaped text, etc.). Optional restricted Markdown support is parsed to an allowlisted AST with links filtered to approved schemes (`https:`, maybe `http:` by host policy); **no raw HTML, scripts, CSS, unsafe image URL, inline event handlers or custom parsers**. Apply context-specific output encoding separately for desktop UI, HTML/web client, telnet ANSI, logs, exported files and notifications. Do not store HTML-escaped data as canonical source text; escaping occurs when emitting to each sink.
- Terminal output strips/encodes ANSI/OSC terminal control sequences, including escape/screen clearing and link protocols unless explicitly generated by trusted rendering layer.
- Do not interpolate text directly into SQL, shell, C# compiler, HTML attributes or file paths. Parameterized persistence; editor upload uses separate asset import boundary and protection.
- User's own long-form text remains visible with preview/counter; UI can paginate or collapse long posts without shortening what the server stored.
- For name/display uniqueness and command keywords, store an independent normalized *comparison key* using a declared, consistent normalization/casefold rule; never infer that this key represents the exact original display bytes.

## Storage and revisions
`SubmitText` carries `requestId`, `contentKind`, `body`, optional `ownerEntityRef`, `expectedRevision`, and client formatting hints that are **not trusted**. Server resolves acting character and write permission, validates text, atomically updates content revision, writes event/outbox and onceKey. On stale edit return `TEXT_REVISION_CONFLICT` with safe merge/retry guidance; never overwrite someone else's description with stale edits. Rate limit applies per principal, target and category even for repeated different request IDs.

## User experience defaults (initial policy)
The [machine policy](../../../contracts/input/v1/default-policy.json) sets separate budgets for command text, quick chat, long RP and character description. These are **not Evennia limits**; they're proposed MudMaker starting values to verify with creator testing. Hosts may choose a higher/lower gameplay cap within supported bounds. A roleplay post may also be a single word. A command (including a complex moderator or builder action) may contain tens of kilobytes of typed argument data; size cannot classify its semantics. The server accepts one **explicitly selected** operation and applies its schema-specific budgets.
