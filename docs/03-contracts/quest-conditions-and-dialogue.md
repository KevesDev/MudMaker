# Quest Conditions, Dialogue Choices and Typed Game Events

**Status:** REQUIRED authoring power, binding condition and dialogue interface. **Owner:** shared Condition Registry + Quest/Dialogue action interpreter + ECS command gateway. **Dependencies:** quest progression/phasing, scripting/graph, narration, commands.

## One reusable condition language
All quest gates, NPC phase rules, exit locks, dialogue option visibility, item usability, spawner eligibility and trigger rules call **the same typed condition evaluator**. No ad hoc `hasQuest` utility per feature and no client-side-only checks.
Canonical expression tree: All / Any / Not / Compare, with named typed predicates:
- `QuestIs(questId, stateSet, ownerScope)`
- `ObjectiveProgress(questId, objectiveId, comparator, value)`
- `QuestFlag(key, ownerScope, value)`
- `HasItem(itemBlueprint, count, ownershipScope)`
- `ActorInLocation(locationId)`, `RegionMatch(regionId)`, `EntityHasComponent(type)`
- `PartyCondition(policy)`, `WorldFlag(key)`, `GameTimeWithin(window)`
- `CustomPredicate(registeredCapabilityId, typedArgs)`
All expressions have immutable versioned definition, diagnostics, explicit actor/observer/world evaluation context and prohibition against unsafe mutating reads. Unknown/missing references reject at publish, fail closed at runtime.

## Dialogue definitions
A versioned `DialogueAsset` binds NPC/object/action to graph starting node and precedence rules, with optional actor/target slots and presentation defaults. Dialogue *session* is per participant (or explicitly configured group), not global current node on Bob. Nodes:
- Speak, player response/options, conditional branch, weighted/random text pool (seeded and deterministic policy), grant quest, set flag, advance objective, open/close quest, award/revoke permitted reward, trigger typed event, wait/continue, go to subgraph, end, and custom script action.
- A dialogue selection must be submitted as authenticated command including dialogue session/node/version/choice ID and expected progress revision. Server rechecks all conditions before running action; malicious clients cannot choose a hidden option.
- Random generic lines on Bob without Talk to Bob active must be per-interaction selection from creator-defined pool; weighting, non-repeat and seed behavior configurable, not hardcoded. Pools should not mutate quest progress unless authored.
- When active Talk to Bob has priority, creator sets `Talk to Bob` progression line and auto-complete/turn-in. Completion may grant `Find Joe` and switch visibility in room B. Dialogue can rejoin and show after-completion reminder based on creator's rule.
- Branch choices preserve typed local variables and per-owner persistent consequences; no result depends on transient in-memory closure that vanishes on reconnect.
- Choices can be optional, exclusive, gated, parallel or dynamically generated by registered API with author-approved limits. Detect dead ends/unreachable alternatives and unhandled default branches before publishing.

## Event and condition evaluation
Only server-committed `ActorInteracted`, `DialogueChoiceCommitted`, `ActorEnteredLocation`, `ItemAcquired`, etc. may credit objectives. Emitting a narrative message cannot itself complete a quest. Script/Blueprint custom event must register typed payload schema and permitted source/actor/target. Exactly when a dialogue command counts as `talk` must be specified: click vs completed conversation vs selected option vs handed-in item; creator selects via dropdown, not ambiguous natural-language matching.

## Data safety and observability
Reward transaction atomicity, duplicate idempotency, event attribution, audience-filtered narration and phase visibility apply throughout. Script capability sandbox applies. Dialogue text escapes rich text and terminal control sequences; variables may expose only allowlisted data, not admin-only component fields. Error code identifies missing option/quest/phase/invalid version and offers player-safe fallback.

## Visual equivalence
Every built-in condition can be authored as a plain-language rule in UI and represented as typed graph data. Example: **Show Joe** → **While** → **Quest "Find Joe"** → **Is In Progress**; advanced creator can replace predicate with a registered script. Both must execute same server-side evaluator. No duplicate dialogue engine for visual vs text.

## Tests
- Bob generic line selected when no quest, and never progresses quest.
- Bob active quest branch outranks generic line; one completed conversation marks correct objective and grants follow-up once.
- Joe visibility and interaction denied for absent/completed states as configured; guessing entity ID does not bypass.
- Concurrent users talking to Bob get independent dialogue cursor and rewards.
- Invalid client choice (unavailable option) rejected atomically; cross-world refs inaccessible.
- Weighted pool reproducibility and optional no-repeat persistence follow configured policy.
- Graph/script equivalence for custom quest action and visibility condition.
- Reconnect and restart preserve decisions and dialogue/quest progress by policy; no duplicate grants.
