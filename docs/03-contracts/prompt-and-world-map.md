# Prompt/status HUD and authoritative world mapping

**Status:** REQUIRED product behavior; proposed versioned wire/schema contracts awaiting S01/S07 ABI decision. **No functionality implemented.** Applies to Creator, Host and standalone Player Client (native and unrelated MUD profiles). References: [Evennia Adding a Command Prompt](https://www.evennia.com/docs/latest/Howtos/Howto-Command-Prompt.html), [Evennia Basic Map](https://www.evennia.com/docs/latest/Contribs/Contrib-Ingame-Map-Display.html), [Evennia XYZGrid](https://www.evennia.com/docs/latest/Contribs/Contrib-XYZGrid.html), [Evennia Health Bar](https://www.evennia.com/docs/latest/Contribs/Contrib-Health-Bar.html). Cross-reference [Player Client](ui-ux/05-player-client-workspace.md), [personal mapper](ui-ux/07-mapper-and-automation.md), [spatial ECS](../02-architecture/spatial-containment-transit.md), [S08](../05-sprints/specs/S08.md).

## 1. Terminology and ownership

**Prompt** means the server-supplied, per-player updated status/information presentation (Evennia's prompt), not an LLM prompt or the command input widget. In a text client it may appear just above the composer, as a fixed status row, or as in-transcript text where required by protocol. A **HUD/status bar** is the native graphical representation of the same authorized status data, potentially pinned top/bottom or divided into movable widgets. **Mini map** is the Player Client presentation of authorized location data; the Creator's world map/room graph remains the editable authority. **Personal map** is a player's independently stored, optional annotations and inferred paths for native or third-party worlds. Do not conflate these.

Evennia can send a distinct prompt with `msg(prompt=...)`, optionally with text, and clients can update a stable position. It may send with each command as a compatibility fallback. MudMaker should maintain the same general promise while using typed native status events and third-party protocol capability detection. Evennia's Basic Map dynamically derives a map from room/exits for a `map` command; XYZGrid links source maps to generated rooms/exits. MudMaker should borrow generation and synchronization principles **without** requiring all MUDs to use a Euclidean grid.

## 2. Creator world mapping foundation

Every world has canonical versioned region/room/exit topology from S05 and authored cell/coordinate/layer hints from S02. No UI-specific parallel topology database. Stable room/region/exit keys, directional and custom exits, one-way links, locked/conditional exits, portals, elevation, moving parent interiors and region boundaries survive save/restore and published revisions. The map renderer queries an authoritative room graph through bounded, scoped APIs; it does not infer structure by parsing room description text. Map symbols, color, label, zone/region layers, category and visibility rules have typed, versioned metadata. Graph-based rooms without coordinates must render as connection diagrams/list; visual cell grid is optional, not a forced world layout.

Creator map editor provides: drag/add room and exit; assign location/area, icon/name/layer and map position hints; mark whether a field is discoverable; preview as selected player/role; publish validated map/projection changes. A Host can configure world defaults for mapping (enabled, disclosed fields, discovery policy, public region overview, visible exits, player annotation policy) and prompt presets. Changes are versioned and validated against topology and rights; preview does not leak hidden exits.

## 3. Server projection API and security

At authenticated join/reconnect and after relevant committed movement, visibility, stat, inventory, quest, weather, or transit changes, server computes **per-observer** projections from committed ECS state; avoid client access to raw database. Proposed typed capabilities, to freeze in S07 protocol ADR:
- `StatusSchema`: widget/key descriptors, stable IDs, labels, units, ranges, format, priority, accessibility text, optional icons, visibility grants; creator-defined extensible numeric/text/enum fields.
- `StatusSnapshot` and `StatusDelta`: entity/player/world generation, monotonic revision, scoped status values and explicitly removed/hidden fields; field-level permissions and lifecycle.
- `LocationSnapshot` and `LocationDelta`: stable visible room/region identity, display label, allowed exit links, direction/label, state if disclosed, optional verified coordinate hints/parent vehicle; map reveal/forget behavior.
- `PromptPresentation`: authorized text fallback/template, optional span semantics, event revision and rendering hints; never executable markup.
- `Capabilities`: schema version, structured-map/status support, optional external protocol extensions and fallback negotiation.

Only committed-authoritative writer events trigger projections. Hide undiscovered destinations, secret paths, private locations and unauthorized stats; do not leak them through counts, IDs, minimap hints, stale caches, reverse edges, search API, client metadata or prompts. Revision-aware snapshots and deltas must survive reconnect, resubscription, world reset, teleport/instance change and map edits without duplicates or stale content. Rate limit updates and coalesce redundant changes, but reliably deliver final state. Client cannot forge world location or vitals; any map-click navigation becomes a validated normal world command. Remote clients cannot publish world maps or change Host prompt templates.

## 4. Prompt design and Creator authoring UX

Every new MudMaker project gets a working **default prompt/status preset** without scripting, with location + exits where authorized and optional basic character vitals. No fixed assumption that every MUD has health/mana; missing values are omitted with graceful layout, not fake zeros. Creator → Player Presentation → **Prompt & Status**: drag/reorder/hide/resize widgets; add plain text, resource bar, numeric meter, location label, visible exits, currency, time, weather, status effect, and typed custom component field; format with labels/icons/colors and units. Bind through searchable safe ECS field selectors and permitted computed summaries, not arbitrary database expressions. Configure global defaults and optional per-role/class/character templates; server policy controls fields while clients control appearance only. Preview real fixture characters, permission roles, dynamic state changes, no-mana class, mobile compact view, screen-reader equivalent, and a text-only generic-client fallback. Validate invalid/missing bindings and overlong values on publish; use one shared ThemeManager token system.

Host Operations: choose/publish prompt preset with immutable release/config lifecycle; safe preview before host starts, without modifying clients. Host data API can read/manage published prompt/map assets locally, not through player connection. Connected players may never upload server-executed prompt templates or reveal hidden fields.

## 5. Player Client customization

Default Play layout supports **persistent customizable prompt bar** (above composer or docked elsewhere), progress meters, icon/text fields, location + allowed exits, and mini map. Each player profile can independently show/hide/reorder/pin/resize available fields, choose number vs bar, typography, color and compact layout, change map scale/follow/notes. Client preferences cannot elevate permission, change server-owned data or install scripts. Offer layout presets, reset, keyboard/tab and touch access. A status bar is not appended as a new transcript line each update unless fallback requested, and prompt updates must not steal focus/clear composer. Separate editable UI presentation from server schema/content.

External MUDs: support native telnet prompt separation (GA/EOR where negotiated), ordinary text prompt, GMCP/MSSP or other independently verified structured status/room hints as available; mapping of custom GMCP keys is opt-in/configurable per-world, never inferred with full certainty. If only plain text exists, show text prompt in transcript/fixed text area when detected without promising HP/location. Structured status/map widgets explicitly say “not supplied by this server” rather than inventing state. Never classify arbitrary incoming server text as trusted UI instructions. Personal mapper can take confirmed native location IDs, GMCP room identifiers or manual observation according to its existing confidence rules.

## 6. Mini map behavior and navigation

Mini map displays current room, discovered/authorized nearby nodes, topology links, icon/area and visible directional/custom exits; supports keyboard alternative list. A creator-authored coordinate/cell grid may provide a spatial backdrop, but never implies physical adjacency where exits are absent. Moving trains maintain stable interior rooms and map context while exterior docking changes; region transitions/teleporters cannot accidentally connect false edges. Fog-of-war/visited room persistence must be per-character if configured by game author. A player's notes/bookmarks are private local profile data, not automatically published to host or shared with others. Navigation click is explicit action, one-step server validation with no client-authority shortcut; route preview and autowalk honor unknown/dynamic/locked exits and stop on failures. Map must handle hundreds/thousands of rooms with bounded spatial/graph windows, paging, level-of-detail and virtualization; never fetch entire private world to render a local region.

## 7. Testing gates and dependencies

- **S04** versioned prompt/map metadata persisted with asset revisions and searchable schema.
- **S05** complete room/exit topology and observer visibility; prerequisite for authoritative map projections.
- **S06** movement/status commands publish committed observer events; text prompt fallback is a real output path.
- **S07** authenticated versioned status/location snapshots and deltas, safe output, reconnect synchronization; cannot claim E2 solely from fabricated UI state.
- **S02** Creator map metadata/preview and reusable theme/status widgets.
- **S08** basic location/exits and prompt visibility in early connected play, then customizable pinned bar/structured mini map after first playable.
- **S09** no-code Creator Prompt & Status editor and world map presentation settings.
- **S13** creator-defined typed C# field/status bindings via same validated ECS API; not direct DB reads.
- **S17** publishing and hosting compatible player-presentation assets; restore and reconnect preserve consistency.
- **S18** permission leak, stale delta/reconnect, large maps, moving interiors, external telnet fallback, mobile and screen-reader audits.

**Concrete user acceptance scenarios:** (1) create two rooms with exits, connect and move, observe location/exits and mini map update; (2) set health/mana then damage/heal via authorized game action, bar changes without duplicating transcript lines; (3) owner customizes a preset and a player customizes their own layout without altering permissions; (4) secret door only appears to approved observer; (5) teleport/board train/dock/undock and reconnect show accurate positions; (6) connect to unrelated plain-text MUD and degrade gracefully; (7) load 10k-room test fixture without global map download; (8) restart host and reconnect without stale prompt or map data. Each handoff has one Builder, separate scoped Auditor and actual focused evidence.
