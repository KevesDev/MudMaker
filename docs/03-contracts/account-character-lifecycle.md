# Account, character, session, access and creation workflow contract

**Status:** REQUIRED product goals, PROPOSED exact design pending owner review/ADR. NOT implemented. Source of truth for implementation phase dispatch: [tracker](../SPRINT-TRACKING.md). One visual workflow graph, **no competing form designer**.

## Evennia source comparison (research, not MudMaker code)

- [Accounts](https://www.evennia.com/docs/latest/Components/Accounts.html), [Characters](https://www.evennia.com/docs/latest/Components/Characters.html), [Sessions](https://www.evennia.com/docs/3.x/Components/Sessions.html): OOC Account is durable distinct from Character (an in-game Object) and network Session; puppeting connects an authorized Session to a Character.
- [Connection styles](https://www.evennia.com/docs/latest/Concepts/Connection-Styles.html): `AUTO_CREATE_CHARACTER_WITH_ACCOUNT`, `AUTO_PUPPET_ON_LOGIN`, `MAX_NR_CHARACTERS`, simultaneous puppet settings; auto-enter, OOC chooser and multiple characters. MudMaker exposes these in Creator preferences and graph templates.
- [Account hooks API](https://www.evennia.com/docs/latest/api/evennia.accounts.accounts.html): `at_account_creation`, `at_first_login`, `at_pre_login`, `at_post_login`, `at_failed_login`, `at_disconnect`, `at_post_disconnect`, `at_post_create_character`, `at_post_add_character`, `at_post_remove_character`, `at_password_change`. Lifecycle timing matters; these are **Evennia names**, not automatically valid MudMaker SDK hook IDs.
- [Signals](https://www.evennia.com/docs/latest/Components/Signals.html): account last logout vs ordinary session disconnect, object post-puppet/unpuppet; do not collapse multi-session events into one generic logout.
- [EvMenu](https://www.evennia.com/docs/latest/Components/EvMenu.html): customizable branching menu patterns; MudMaker exposes one typed workflow graph, without an additional authoring form editor.
- Evennia permission strings, lock predicates and Builder/Admin levels inform extensibility, **not** reliance on privilege names as the sole security model. Permissions must be fine-grained capabilities, scoped grants, explicit denials, and host hard limits.

## Canonical identities / data

`WorldId`, `AccountId`, `CharacterId` and `SessionId` are **different opaque stable identifiers**. Account IDs are generated on committed registration, never derived from username, email, display name, sequential public index or currently connected Session. All references are world/tenant-scoped and generation/revision checked where applicable. Account rename, character rename, login name changes and credential reset never change AccountId. Usernames/emails are mutable lookup attributes with uniqueness/conflict rules, not referential keys; account ID is never a substitute for authentication. Never expose internal database primary keys in lieu of a versioned public opaque ID. Export/import maintains old-to-new identity mapping and refuses collisions. Audit/rewards, bans, roles, character ownership, private messages, creator approvals, and OOC state reference AccountId; physical game world state references CharacterId/ECS EntityRef and retains owning AccountId as a verified relationship. Guest accounts and recovery must have explicit expiration/ownership policy. No accidental reassignment on delete/recreate or rename.

Distinct services: AccountIdentityService (registration, credential hashing, reset/verification, lockout, MFA optional, account lifecycle); SessionService (authenticated session, revocation, timeouts, per-device state); CharacterRosterService (owned chars, slots, roster claims, attach/detach, last-used/last-safe location); AuthorizationService (roles, capabilities, scopes, policy decisions, audit); CharacterCreationWorkflowService (versioned graph, durable execution cursor/state). All writes through bounded authenticated host-local API or world-authoritative transaction gateway. Remote clients never query raw DB, choose AccountId in command payload as authority, set permissions, attach another account's character or evaluate secret password conditions. Owner app can manage permissions via local admin capability; remotely connected player interfaces cannot acquire Host privileges.

## Lifecycle, in the correct order

**Registration:** anonymous bounded request → normalize identifiers, validate uniqueness/invite/policy → secure credential verifier and anti-abuse checks → create AccountId/account atomically → optional verification → account-ready. A newly registered Account need not yet own a Character. Registration hook sees only approved metadata; no plaintext password, credential verifier, email token or IP unless specific redacted authorized context. Hook failures cannot bypass secure defaults.

**Login:** transport/session admission → credential challenge and verification → policy checks (ban, disabled, MFA/verification) → authenticated Session bound to immutable AccountId → OOC lobby, auto-puppet eligible last character, or launch creation graph as configured. Never run untrusted user-authored C# to decide whether a password is correct or whether a revoked session is authenticated. Multiple sessions and one-character-at-a-time settings must be atomic, race-safe.

**Character creation:** quota/approval/name/ownership checks → reserve slot and versioned workflow run → menu choices, point buy, RNG/re-roll budgets, existing roster, in-world room/item/NPC events, roleplay/application review → commit validated CharacterId and owner linkage once, or incremental provisional ECS character with explicit limited capabilities. Durable suspended graph supports reload/reconnect, multi-day progress, retry, cancel/review. Never duplicate starter equipment or grant points on replay, event redelivery, or worker crash.

**Puppeting / selection:** authorized AccountId + CharacterId + SessionId → check ownership/claim/grant, world state, active puppet policy, lock and slot limits → attach session → resolve last safe room/fallback spawn per policy → deliver player-specific snapshots. Switch and unpuppet are distinct transitions. Account permissions do not automatically equate to character roles/attributes.

**Logout:** explicit logout vs abrupt disconnect, session revocation, final-session logout, character detach, offline/persistence and reconnect policies are distinct events. Preserve last committed location, avoid moving a character on transient loss unless game design says so; no scripts after the session's privileges are invalid. Multiple sessions: one disconnect must not be mistaken for Account's final logout.

**Deleting/removing:** disable, anonymize or delete per retention/privacy rules; preserve referential integrity and immutable audit identifiers; detach all sessions safely and revoke grants. Creator-facing recovery tools must not permit credential or identity takeover.

## Permissions / Creator UX

Creator **Accounts & Access** workspace: account lookup by display identity and opaque ID, scalable pagination, linked characters and sessions, last activity, disable/reset/revoke, audit history. One Role/Capability editor offers built-in Player/Helper/Builder/Moderator/Admin templates plus unlimited custom roles and fine-grained action grants. Scopes may bind region, zone, entity ownership, command, world, moderation targets and creator-only asset types. Show effective permissions and explanation (“allowed by Region Builder for Area A”, denied by Owner restriction), dry-run as test identity, audit before/after role changes, conflict warnings and two-person/re-auth confirmation for high-risk changes. Never use a permission check only in UI; all protected actions check server-side. Explicit owner/root protections cannot be overridden by world-creator scripts.

Creator chooses login behavior from presets: auto-create+auto-enter, multi-character selection, in-world onboarding, staff approval, prebuilt character claims, guest/demo; all are configurations/templates of same engine. Account registration policy independent from character creation. Player lobby supports new/resume/choose/request/review; third-party MUD profiles keep external authentication isolated.

## Single visual workflow graph

Use the existing shared typed graph editor and asset publisher—**not** a separate form authoring system. Nodes: registration/completed login/first login/character selected; choose option/text, allocate points, roll/reroll, branch, repeat/validate, wait for staff review, on enter room/on item pickup/on NPC dialogue/on quest event; assign fields, bind equipment, spawn, grant starter role, move, finish/suspend/reject. Input nodes render suitable graphical controls or text/menu equivalents; in-world nodes use real authoritative ECS events. Every graph step has typed schema, bounded execution, versioned continuation and localized accessibility text. The inspector is ordinary node configuration, not a competing wizard designer. Custom C# hooks attach only through approved typed binding/capability gateway. Workflow may last across sessions, and completion is creator-defined, not synonymous with account registration.

## Scripting and hooks — **version compatibility critical**

Current [canonical registry](scripting-v1/03-hook-registry.md) and [hooks.v1.json](../../contracts/scripting/v1/hooks.v1.json) already contain `player.login.after`/`player.logout.after` and source-level Evennia counterparts. **Do not silently register new IDs in prose.** New planned lifecycle event families, requiring reviewed registry JSON + CLR `Contracts.cs` + Protobuf wire case + exact SDK signatures + source catalog + negative tests before use:
- account: registration request/committed, verification-completed, first login, login denied, login established, final logout, role changed, account disabled/deletion requested; only *after* for security-sensitive verified facts.
- session: login attached, disconnected, revoked, reconnected; include safe disconnect reason and final-session boolean; event identity/session context cannot be forged.
- character: provisional created, finalized, roster attached/removed, selected/puppeted, unpuppeted, switch, last safe location restored, archived; after committed facts, before only for game-policy choices which cannot override ownership checks.
- creation workflow: started, step presented, choice validated, points allocated, deferred event observed, approval submitted/approved/rejected, completed/cancelled; typed workflow/run/step identifiers and replay-safe onceKeys.
- permission: evaluated (diagnostic read-only, guarded against recursive checking), role-grant/revoke after commit, region-capability change; scripts never gain authority by responding “allow” to a host-security invariant.

Suggested namespace examples **NOT REGISTRY IDs until versioned review**: `account.created.after`, `account.login.after`, `account.logout.last.after`, `character.puppet.after`, `character.creation.completed.after`, `character.creation.step.before`, `role.changed.after`. Explicitly decide where existing `player.login.after` and `player.logout.after` live (session vs account), with compatibility aliases if changed. Never conflate Evennia method names with MudMaker canonical IDs. Hook context uses opaque AccountRef/CharacterRef/SessionRef and deliberately permitted metadata only; no password hashes, reset tokens, session secrets or private email; strict per-owner capability restriction. Before hooks may validate/change *game creation choices* but cannot bypass authenticated identity, ownership, quotas, consent or permission denials. After hooks may propose idempotent separately validated effects only.

## Evennia ID visibility and transport security — verified clarification

Evennia's `DefaultAccount` documentation explicitly exposes a read-only integer `dbref` / `id` at the **server-side API** level. This does **not** establish that a game must send it to ordinary players, nor that its mere disclosure compromises an account. Do not claim that Evennia universally hides Account IDs for security. [Account implementation](https://www.evennia.com/docs/latest/_modules/evennia/accounts/accounts.html), [Account model](https://www.evennia.com/docs/latest/_modules/evennia/accounts/models.html).

**MudMaker policy:** immutable, opaque, world-scoped AccountId is a durable relationship key, **not a credential and not an authorization token**. Keep it out of ordinary login screens, world text, prompts, public profiles, Telnet/GMCP metadata, and client diagnostics by default. Internal AccountId is available only to authorized local Host/admin routines and narrowly permission-checked APIs/hooks. A player's own identifier, if needed for a client feature, should be a separate stable per-world public reference with a constrained scope, not the internal DB primary key. Avoid enumerable public identifiers. Even accidental disclosure must not permit login/puppet, role changes or account enumeration. Every sensitive operation resolves the AccountId server-side from its authenticated session.

### Login and network trust boundary

Evennia: an unauthenticated Session is created at connection, runs an unlogged-in command set, then links to an Account after successful authentication; the Account may puppet a Character. It supports multiple Sessions and distinguishes physical disconnect from an account's last logout. The portal handles protocol-specific Telnet/SSL/SSH/web transport; its server session handles game state. References: [Sessions](https://www.evennia.com/docs/latest/Components/Sessions.html), [Accounts](https://www.evennia.com/docs/latest/Components/Accounts.html), [Connection styles](https://www.evennia.com/docs/latest/Concepts/Connection-Styles.html).

**MudMaker protocol policy:**
1. On connection assign a short-lived opaque connection/session handle with no Account or Character privileges. Do not allow client-supplied AccountId or CharacterId to become an authenticated identity.
2. Use an encrypted authenticated transport for passwords, reset tokens, MFA and durable login credentials (native TLS/WSS; Telnet over TLS or other approved secure protocol for compatible clients). Plain Telnet must be explicitly identified as insecure: disabling terminal echo hides local characters but **does not encrypt wire bytes**. Do not present plaintext password login as secure. Creator-facing Host setup must warn/block insecure public credential flows under the final approved security policy.
3. For a conventional Telnet login, handle password input with protocol-compatible echo suppression and restore echo on every completion/failure/abort; avoid embedding passwords in echoed one-line `login name password` commands where secure alternatives exist. Rate-limit pre-auth attempts. Never write plaintext credentials or full auth command lines to transcript, logs, automation history, analytics or exception output.
4. After server-side credential/verification/MFA checks, bind the Session to the Account. A subsequent character select sends only a requested target reference; server authorizes ownership, active puppet limits and world policy before attachment. A character's in-game ID and name are not account authentication.
5. Login may end in an OOC lobby without a character, or auto-puppet one allowed character; a new Account may have zero characters. Explicit logout, disconnect, last-account-session logout, server restart/reconnect and unpuppet have separately defined lifecycle/hook events.
6. Reconnect/session resumption requires fresh server-validated binding and revocation checks; a previous session ID alone is not bearer authentication. Rotate short-lived secrets, invalidate expired/revoked connections, prevent two concurrent claims from bypassing puppet limits.
7. Third-party MUDs connected through MudMaker Play keep remote credentials in **per-profile client-side protected storage**, not MudMaker-host's world database. A remote MUD cannot access Creator privileges or MudMaker host account IDs. Warn for plaintext Telnet and do not store secrets in exported profiles by default.
8. Client/server messages should contain only the identifiers necessary for the authorized operation. Public structured game metadata, GMCP and map/status deltas may convey permitted character/room references, never hidden AccountId, password hash, session bearer token, recovery token, or owner staff secrets.

**Evidence gates:** sniff authorized plaintext Telnet fixture to confirm password exposure and correct warning; test TLS route for confidentiality; check transcript/log redaction, echo restore on error, account enumeration, identifier swapping, cross-account puppet attempts, session fixation/replay, multiple-session logout ordering, failed-login timing, rate limits and revocation. E2 loopback is not proof of safe public Telnet authentication.
