# Local database lifecycle, storage API, recovery and Creator Data Manager

**Status:** REQUIRED product/UX/security constraints; binding embedded storage and data management contract; actual engine/transaction implementation pending. **No database functionality is claimed implemented.** This specification complements [state persistence](../02-architecture/state-persistence.md), [ECS authority](../02-architecture/ecs-core.md), [hosting](../04-features/hosting-and-admin.md), and [scripting state](scripting-v1/04-references-and-state.md).

## 1. Owner experience and non-negotiables

Creating a project automatically creates an empty but fully configured *local* durable store, its schema and required indexes. Opening an existing project validates/updates the schema safely; Host starts required storage without a terminal, SQL knowledge, separate database download, administrative login or manual database configuration. Host keeps the store open and available throughout its lifecycle and flushes/closes cleanly on shutdown. The selected v1 store is **bundled in-process SQLite with WAL**, project-isolated ownership lease and atomic migration/recovery; S01/S04 verify concurrency, locking, filesystem, migration, durability and backup behavior before delivery. **Hard requirement:** no separately installed services or tools of any kind. The shipping application must embed and directly manage its database engine in-process or through a fully bundled internal component. Docker, PostgreSQL server installs, MySQL/MariaDB installs, container runtimes, Python, manual migration CLI, external service managers and externally downloaded runtimes are never prerequisites to creating, playing or hosting. No database port or external DB credentials. A compatible library may be embedded; building a brand-new SQL engine is not required. Each project has isolated storage and an explicit ownership/locking model.

**Local database access only:** the host application and its supervised local engine/storage services can open the database files, IPC endpoint or local driver. Never bind a raw SQL/DB port on LAN/public interfaces. Never expose database driver, query language, table introspection, database credentials or arbitrary SQL through connected clients, user-created game scripts or remote admin APIs. A remote player may request *gameplay actions* over the authenticated game protocol, which are checked by the server command/ECS gateway. The host's Creator/Host UI may use a privileged **local app API** with OS process/user, per-project and role capability checks. A loopback HTTP endpoint alone is not proof of local authorization: require peer/auth token, origin/CSRF controls where browser-based, short-lived session scopes and no external bind; prefer authenticated same-process/IPC where feasible.

## 2. Data ownership and schema boundaries

Distinguish (a) versioned authoring assets: Blueprints, maps, dialogue, quests, command definitions and scripts; (b) durable runtime ECS state: entities, component values, parent/room relations, dynamic exits, world event timers, inventory and player/quest state; (c) accounts, permissions, audit/operational data; (d) transaction outbox, onceKeys/idempotency, schema and release manifests; and (e) cache/derived indexes that can be rebuilt. Ownership and storage of each category must be explicit in S01 ADR and S04 design; do not silently conflate project draft, immutable published release and current live world. Do not store live scripts as executable input from remote users. Type-safe schema IDs, stable entity IDs with generations, versioned asset GUIDs, foreign reference integrity, expectedRevision/optimistic conflict checks, and world/project isolation are mandatory.

Like Evennia's typed persistent Objects/Accounts/Scripts/Channels, Attributes, Tags, aliases and access locks, support *discoverable* typed records with indexed fields/tags and extensible typed component data; MudMaker uses its approved **composition-first ECS**, not Django/Evennia typeclass inheritance. Attributes and searchable tags should remain distinct concepts, with documented index/key/category semantics and migration policy. Provide nonpersistent runtime/cache state explicitly rather than accidentally writing every temporary value.

**Only the authoritative world writer commits live mutations.** All sources (creator app, command client, local compiled C# worker, graph, admin UI) produce validated typed intent/effect commands into one service. Persist state changes, idempotency receipt and outbox event atomically as applicable. Deliver committed events after persistence. Enforce ownership, grants, visibility, bounds, schema and referential integrity server-side. No direct SQL from C# hooks or graphs, including local owner scripts.

## 3. Provisioning and migration state machine

Project Create → ensure project-local writable data directory (prevent traversal/symlink escape) → establish exclusive ownership lease → create temporary fresh store → execute versioned bootstrap migrations/indexes → validate identity/schema and integrity → atomic activation → usable project. Reopening: detect store, lock, validate engine/store version and space/permissions, obtain safe pre-migration recovery point, migrate transactionally when supported (or staged copy/atomic switch), verify, then activate. On failure **leave original unchanged** and offer an understandable Retry / Open Read-Only / Restore Backup choice, subject to verified safety; never silently reset or replace a nonempty database. Reject opening newer incompatible schema versions with explicit guidance; record migration history and release compatibility. Avoid running destructive migration while live; Host startup preflight refuses to open player ports until storage ready.

Default experience: “Preparing your world…” and progress/error explanations, not database jargon. Support crash interrupted provisioning/migration, wrong OS permissions, disk full, corrupted data, incompatible releases, concurrent processes, and project moved to another machine. Never claim successful recovery on a mere process restart. Provide precise, testable startup states and errors.

## 4. Local API (contract sketch, not yet wire ABI)

Local **CreatorDataService** capabilities: ListCollections(kind, project/world, filters, cursor, sort); GetRecord(id, revision); QueryRelationships(id, direction, cursor); GetSchema(kind); ValidateDraft/PreviewChange; Create/Update/Delete with expectedRevision, validated typed payload, owner capability and audit; BatchPreview/BatchApply with chunking, idempotency and per-item results; ExportFilteredSelection. Do not expose arbitrary SQL or raw DB handles. Schema-driven UI forms map to existing ECS/asset authoring services; the Data Manager must not become a second mutation authority.

**World runtime** operations are distinct typed effects (spawn/create entity, set component field, adjust number, attach/move, grant reward, change quest, schedule event); route through world writer, never directly through Creator CRUD. Read endpoints must enforce per-user authority and redact secrets (password/hash, tokens, player private state, server quiz answers). API requires deterministic pagination with stable unique tie-breaker, cancellation, explicit field whitelist, query limits, streaming/backpressure where needed, audit and revision conflicts.

## 5. UX: Data Manager for hundreds or thousands of records

Expose a **World Data**/Data Manager workspace from Creator, not a raw database console. Default home: searchable groups (Worlds/Regions/Rooms/Exits; Entities/Blueprints; Players/Characters; Items; Quests/Dialogue; World Events/Spawners; Commands; Tags; Releases; Health/Backups), each with counts and a contextual create action. Lists use server-side paging/keyset cursors, virtualization, bounded preview data, fast indexed search, sortable fields, type/region/tag/status filters, saved views, hierarchical navigation and breadcrumbs. Avoid loading all records to the browser or listing a thousand giant cards. Search must work on both IDs and human-friendly labels; allow duplicate names with visible stable IDs. Add command palette and keyboard navigation as well as touch-friendly selection.

Selecting a record opens a schema-driven inspector with human labels, help text, component tabs, links to referenced records/where-used, revision and last-modified metadata, validation errors and a **View in Map / Open Blueprint / Test in Player** action where appropriate. Distinguish immutable published release data, editable draft assets and live runtime state visually, with correct permissions. Edits offer undo for uncommitted drafts; committed change uses explicit transaction and, where supported, reversible change history. Bulk select/filter/preview/edit/archive/delete with number of impacted records, confirmation, referential checks and progress/cancel behavior. Warn before changes affecting active players; no mass silent deletes or accidental cascades. Preserve search/filter/scroll across navigation, offer accessible feedback and a useful empty state.

For high volume, define measurable S02/S09 acceptance fixtures (e.g. 1,000/10,000 mixed records) and latency/scroll memory budgets in a verified platform ADR; do not invent fixed performance guarantees. Loading and error states should remain responsive under query cancellation or service failures. No database terminology is required for routine user actions.

## 6. Backups: optional, discoverable and safe

Backups are **opt-in**, configurable in Host → World Data → Backup & Recovery: manual **Back Up Now**, optional scheduled backups, retention count/age/storage budget, local destination picker, status and last verified backup. Default **no mandatory account, cloud upload, external process, terminal or additional software**. Before optional automatic scheduling is enabled, clearly show disk consumption and privacy implications. A safe manual export should be available whether or not scheduled backup is enabled.

A backup captures a **consistent point-in-time snapshot** across required ECS/database files, project/release manifest, asset versions and schema/migration metadata, plus outbox consistency; where files are separate, use coordinated checkpoint/transaction/snapshot strategy. For a write-ahead-log store, never copy only the primary DB file while active. Snapshot must be compatible with active hosting without arbitrarily disconnecting players; if online consistent snapshot is unsupported, show an explicit safe pause and do not misrepresent it. Include integrity/hash verification, format/version, timestamp, project/world identity, platform and required release compatibility. Backup archive may contain sensitive player information: default local destination, restrict filesystem permissions and describe optional encryption/password recovery, with the versioned authenticated backup encryption profile selected in Host security settings. Backups stored outside the mutable live DB path by default; prevent a backup from overwriting the live store.

Restore workflow: Browse verified backups (including external backup file) → inspect date, project, release, compatibility and validation status → choose **Restore as Copy** (safer first choice) or Replace Current World → warn about lost later progress and connected players → create a verified rescue snapshot of current state if possible → quiesce world writer/disconnect only when necessary → restore to staged location → verify schema/integrity/references and migrations → atomically activate → resume and verify gameplay. **Failed restore must keep original active state intact**. Offer named fallback to last *verified* compatible backup only with owner consent, never silently roll back a current world. If a store is corrupted on startup, detect, enter safe recovery screen, identify backups and last good checkpoint; do not automatically choose an older snapshot. Test power-loss at each swap, wrong-world backup, tampered archive, missing parts, full disk, incompatible version and restore after a game release upgrade.

Backups are not the same as crash recovery, database transaction durability, release rollback or player-facing save slots. Distinguish all four in UI.

## 7. Operational management and QA

Host UI: database Ready / Starting / Migrating / Busy / Recovery Needed status; world records and approximate storage footprint; recent snapshot status; connection/runtime health; maintenance actions (verify integrity, compact only when safe, rebuild derived indexes, export support diagnostic with secrets removed). Database stays active while host runs, with single-writer contract and bounded reads. Shutdown flushes/checkpoints safely; crash recovery replays committed log/outbox without duplicate rewards. Do not expose raw DB file delete/reset actions in normal UX.

**Acceptance matrix:** fresh project offline on every supported OS; no Docker/container engine or external database/runtime install; owner-only local open/IPC; attacker on LAN cannot address DB; remote player cannot query arbitrary records; 1k–10k searchable mixed records; create/edit/bulk/update with permission and revision checks; script/graph effects via writer; restore consistent backup under active writes; staged restore rollback on failure; schema migrations and old/new release compatibility; app restart, abrupt kill, process contention, disk full, file corruption, player join during preflight, privacy redaction, optional retention and no-backup mode. Audit actual behavior and command evidence; documentation is not implementation.

## 8. Evennia references and deliberate differences

- [Choosing a Database](https://www.evennia.com/docs/latest/Setup/Choosing-a-Database.html): default self-configuring SQLite file with PostgreSQL/MySQL alternatives; MudMaker goes further by removing SQL/server setup from normal Creator UX.
- [Typeclasses](https://www.evennia.com/docs/latest/Components/Typeclasses.html): database-backed Accounts/Objects/Scripts/Channels, handlers, persistent vs nonpersistent attributes and cached objects. MudMaker maps concepts to ECS and explicit versioned state, not Python class hierarchy.
- [Tags](https://www.evennia.com/docs/latest/Components/Tags.html) and [Attributes](https://www.evennia.com/docs/latest/Components/Attributes.html): shared indexed categorization vs per-record values; inform searchable component/metadata API.
- [Updating Evennia](https://www.evennia.com/docs/latest/Setup/Updating-Evennia.html): explicit migration/version handling; MudMaker must automate safe migration under supervised app lifecycle.
- [Evennia Setup Overview](https://www.evennia.com/docs/latest/Setup/Setup-Overview.html): server operations baseline; MudMaker targets a GUI-first no-terminal path.

**Research-derived comparison, not a claim of existing MudMaker implementation.** Evennia is a capability benchmark; do not copy its schema, Django ORM, Python API or operator CLI into an ECS-native product.

## 9. Sprint placement / dependencies

- **S01:** storage engine, concurrency, file layout, locking, schema versioning, native durability and recovery ADRs **before S03–S04**.
- **S04 (storage foundation):** automatic DB provisioning, record persistence, indexes, migrations, atomic snapshots, host-local data API and restore safety *before* S05/S06/S07 depend on persistence.
- **S02/S09:** navigable database management shell, searchable paginated collections, schema inspectors and safe bulk tools; Editor actions reuse S04 API and existing command/asset services.
- **S07:** loopback-host persistence readiness, no remotely reachable database, remote data isolation.
- **S13:** worker-typed effects only, no raw DB access; persisted C# overrides and recovery.
- **S17:** supervised hosting DB lifecycle, optional backup schedules, backup browsing, safe fallback restore and diagnostics, remote hosting gate.
- **S18:** full cross-platform, concurrency, security, high-volume and disaster recovery audit.

No new separate giant “database sprint”: database foundations belong early in S04, management belongs in Creator work, hosting/backup lifecycle belongs in S17. All tracker phases retain central status/evidence ownership.

## Universal template library persistence

[Canonical template management and variations](reusable-templates-and-variants.md) use the project's embedded DB and immutable published asset revisions. Persist folders, tags, searches/saved views, lineage, instance overrides, aliases, audit and where-used indexes across reopen/restart/backup. Rename by stable ID; delete only unreferenced draft assets after review; archive otherwise. S04 stores/indexes it and S09 exposes the full searchable graphical library.

**Tag persistence implementation:** [Universal tags](universal-tags-and-organization.md) use project-owned `TagDefinition` and `TagAssignment` tables with durable IDs, indexed target/namespace/key lookups, expected-revision mutations, audit, restore, rename/merge, and safe reference checks. Every asset type (including C# file catalog records and commands) can be tagged through the same data service. Gameplay tag runtime assignments are published ECS mutations and never inferred from editor organization labels.
