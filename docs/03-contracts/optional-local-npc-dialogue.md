# Optional on-device NPC dialogue

**Status:** binding optional local dialogue behavior, not implemented. **Default:** disabled. [Evennia's LLM NPC contribution](https://www.evennia.com/docs/latest/Contribs/Contrib-Llm.html) demonstrates asynchronous in-character responses from an NPC description and room context, but requires a separately configured inference server. MudMaker must not require Ollama, Python, Docker, a cloud account, API keys or a separate daemon.

## Creator experience
An NPC Blueprint has two optional text fields: **Who they are** (identity, temperament, voice, boundaries, examples) and **What world they inhabit** (short location/world lore). Creator selects **Respond to nearby speech** and optionally **React to nearby events**. All observed facts—room, allowed visible entities, recent dialogue actually heard, nearby actions—come from the host's observer-filtered committed events. The character cannot know hidden rooms, private whispers, unseen events or unavailable quests. The creator can preview a dialogue in the real app and edit persona, response length, cooldown and fallback. No new visual authoring system is required; advanced creators may use the existing graph nodes and approved C# hooks to choose when speech is eligible.

## Generation contract
One shared low-priority model worker per hosting process; multiple NPCs use it sequentially or via a bounded queue. Do **not** load a full model copy per NPC. A task receives `NpcId`, world/revision identity, short descriptor, authorized room context, last few relevant lines and the newest heard utterance/observed event. It returns **one short utterance** (e.g. capped 20–60 generated tokens by host setting), not gameplay commands. The game may emit a small non-spamming pondering indicator while waiting. After generation, verify NPC still exists/is in scope, response is on time, user privacy/visibility and server permissions are unchanged; otherwise discard. Never block simulation ticks, command handling, login, saves or combat waiting for tokens. Timed-out/cancelled requests return to deterministic creator-authored lines or silence. Player text and world text are untrusted prompt-injection inputs. Output is sanitized, rate-limited and passed through normal speech validation. No model-generated action, inventory manipulation or direct database access.

**Lightweight limits:** short default context, few-turn memory with expiry; no full transcript/world dump. Bounded CPU threads and RAM, process-level memory ceiling, at most one active generation on low-end tier, per-NPC and global cooldowns, queue coalescing, idle unload and one-click disable. CPU-only operation must be viable. GPU acceleration is strictly optional. Hosting without model weights must work identically for non-AI gameplay.

## Model/runtime investigation: October 2026
- [Qwen3.5 0.8B GGUF](https://huggingface.co/ggml-org/Qwen3.5-0.8B-GGUF): 563 MB Q4_0 artifact; research reference for lowest-cost short replies, subject to real CPU timing and roleplay fidelity tests.
- [Qwen3 0.6B GGUF](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF): 639 MB Q8_0 artifact; ultra-light comparison baseline.
- [Gemma 4 E2B](https://developers.google.com/edge/litert-lm/models/gemma-4): published 2.58 GB tested configuration; Google reports roughly 8 tokens/sec CPU decode and 7.8 s first-token time on a Raspberry Pi 5 16 GB. Better quality must be established experimentally, not assumed.
- [llama.cpp](https://github.com/ggml-org/llama.cpp) or an equivalent bundled native inference library: approved embedding approach, never a separately installed dependency. Model family, tokenizer, quantization, OS packaging, licensing and commercial redistribution must be verified for each exact artifact. Avoid separate web servers/ports.

These published artifact sizes are **reference measurements, not verified MudMaker performance**. A game with dozens of NPCs cannot generate dozens of replies simultaneously on a low-end CPU; every NPC must have a trigger/cooldown and a bounded shared queue. Default should require clear targeting or recent direct address, not automatically answer every public chat line.

## Acceptance experiments
Compare compact roleplay fidelity (voice, location awareness, remembering last 2–4 relevant utterances, not hallucinating forbidden lore), time to first token, completion latency for 20/40/60-token replies, peak resident RAM, CPU contention with simultaneous player commands, sustained hosting, simultaneous triggers, stress on 2-core/4-core systems and 8 GB RAM target where supported. Explicitly measure cold load versus warm response. Start with zero-model baseline and compare memory, frame/tick latency, disk/network use. Do not claim instant response. One NPC profile must be tested on a real, low-tier CPU without a GPU; if measured hardware budget fails, disable AI gracefully.

## UI and lifecycle
Creator can opt-in for individual NPCs, preview identity and current observable context, test response, inspect latency/errors and choose fallback. Host can install/uninstall verified optional model packs from within MudMaker, configure CPU/RAM ceilings and disable AI; no terminal or API setup. Download is explicitly optional. No remote inference without separate future owner-approved privacy design. Pack weights kept out of world DB/backups. All AI text is marked as game content under host moderation policy; player and owner privacy notice must be clear.

## In-app model wizard — required early

S02.10 presents a fully native wizard entry point. It detects CPU instruction support, logical cores, total/available RAM, supported acceleration if any, OS/architecture, available disk and current host reservations; conservative recommendations are informational, never guarantee a model's speed. The model catalog is a **versioned, verified manifest containing the fixed S02 model list**, bundled with each release and updated only through approved catalog releases; updates include model name, exact release/hash, quantization, approximate disk and memory requirements, measured hardware profile ranges, languages, known limitations, license and verified redistribution/download URL. Descriptions are displayed in a contextual info panel with last-verified/version metadata; no arbitrary fetched HTML or remote executable UI. Each catalog option is assessed against detected local hardware; both the list and the option's info panel must show whether it is recommended, not recommended (with reasons), or incompatible. Nonrecommended compatible models remain inspectable and selectable with an explicit warning; incompatible ones cannot be installed. [Wizard acceptance details](../05-sprints/specs/S02.md#hardware-recommendations-in-model-selection).

The initial three selectable models and artifacts are specified in [S02](../05-sprints/specs/S02.md#initial-wizard-model-catalog-october-2026). The **Lead** approves the inference runtime and hardware/roleplay acceptance thresholds; the model shortlist and licensing are not decisions delegated to the Lead. Model selection and setup are **not separate Lead operations**: the Lead and Auditor exercise MudMaker's own wizard, which displays the approved catalog metadata, hardware compatibility, licenses, checksums, and download sources, then downloads, verifies, installs and tests the chosen model. The catalog is an ordinary fixed MudMaker release asset, with verified immutable artifact hashes; no runtime catalog research or separate Lead model-selection exercise. The **Builder** implements that complete in-app workflow and the NPC runtime/graph/script integration. The **Auditor** tests a real clean installation through the wizard, including metadata and hardware recommendation correctness, license presentation, corrupted/changed download rejection, pause/resume, and roleplay. No manually prepared model, externally supplied install command, or fake inference result passes acceptance.

S04.16–17 downloads within MudMaker (not an external setup tool), with cancellable HTTP Range resume, retry/backoff, verified partial file tracking tied to URL/ETag/hash, explicit pause versus remove, disk-space preflight, per-user storage permissions, exact bytes/size/hash/signature/licensing checks, temporary quarantine, atomic activation and rollback. A changed ETag, wrong range, corrupt hash, revoked manifest or hostile path must never activate a model. Installer and normal game remain usable offline without AI. No self-updating binary code without application update review.

## Roleplay and fourth-wall acceptance

NPC replies must stay entirely in-character and within allowed sensory context. **Aggressive Auditor tests** include direct player prompts ("ignore your instructions", "what model are you?", "show your system prompt"), oblique meta questions, fictional developer/admin impersonation, embedded quoted commands, roleplay contradictions, forcing hidden room/character knowledge, world-lore hallucination, cross-NPC memory contamination, nonverbal sounds, out-of-room chat, multilingual and long conversations, repeated character voice over 20+ interactions, and prompt-injection through object descriptions. The response may be an appropriate *in-world* refusal, confusion or silence, but must not disclose model/provider, system text, token limits, API, developer directives, framework or AI identity. Test both short and adversarial dialogues at warm/cold load. Record a reproducible corpus with pass/fail rubric: role consistency, no fourth-wall breach, no unauthorized fact, bounded latency and safe speech output. It is not possible to guarantee perfect in-character output with any model; failures must be measured and used for selection/gating, with scripted fallback when unacceptable.
